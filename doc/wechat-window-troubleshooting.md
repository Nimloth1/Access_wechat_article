# 微信主页读取故障排查（2026-09-05）

## 本次修复

截图中的“未找到公众号主页窗口”发生在启动 MITM 捕获之前。原因是本地
Win32 枚举优化返回的 `WindowInfo.control` 为空，但查找器先要求读到文章才
允许选中窗口，UIA 控件却在选中之后才挂接，形成了无法通过的条件。

恢复上游的职责划分：先根据微信进程、窗口类名、标题和可见性定位候选窗口，
再挂接 UIA；由主页扫描服务激活窗口、读取公众号名称和文章。
保留 Win32 快速枚举，避免重新遍历整个桌面的 UIA 控件树。
同时移除旧编排入口对已不存在的 `home_find_use_article_probe` 配置的引用。

连续采集还发现新版微信主页将日期行和文章卡片平铺为兄弟节点。旧解析器把
整张列表误认成“今天”的一个日期组，导致“昨天”等日期行变成 `xxx` 伪文章，
点击后等待文章打开超时，后续文章的日期也被错配。

日期读取器现同时支持平铺结构和原有嵌套结构；日期行只划分文章归属，不能
进入点击队列。日期组范围覆盖其文章，因此日期行滚出视口后仍能识别组内文章。

还修复了关闭确认把连续几次 UIA 不可读或“加载中”当成成功的问题。
现在必须稳定读到返回页面的实际标题，才允许释放前台任务并点击下一篇。

## 2026-09-06：任务数 0 与日期边界连续采集

用户提供的 16:28 失败日志中，第一篇返回后，第二篇沿用同批快照坐标，
随后报“未检测到已打开的文章标签”；这个终止错误没有唤醒前台等待，
最后被主流程显示为“单篇任务未在规定时间返回前台回执”。
`recordLimit=0` 本身已正确表示不限数量，日期条件也保留包含边界当天的语义。

修复后每篇返回主页都重新扫描，使用最新卡片坐标；展开“余下文章”时也丢弃
展开前的坐标。已处理文章通过指纹去重，任务编号只随实际处理推进。
发现日期边界时先处理同屏所有符合条件的文章，再结束扫描。
